# Изменения моделей и уточнение плана

14.11.2026. **Исходное дерево FIDO2Verif не изменено.**

## Пилот привязки PinToken

Raw `20261114T173318892199Z-pilot-original-token-14067f66`: исходный `query secret PinToken.` успешно разбирается ProVerif 2.05. Он охватывает несколько развёрнутых одноимённых bindings: RESULT содержит PinToken, PinToken_1 … PinToken_10. В распечатанном process видны как fresh name CTAP_Authnr, так и переменные извлечения токена. Это не syntax ambiguity и не запрос только к неиспользуемому fresh name из шаблона. В E0 ProVerif доказал совокупный запрос.

Поэтому предлагаемое на ранней диагностике переименование токена **не применяется** и не включено в надстройку. Основная матрица сохраняет исходный запрос со всеми его bindings. False нужно объяснять по конкретному trace, не автоматически приписывать одному binding.

## Основная матрица

12 inputs сформированы оригинальным `Case.write_file(False)`: query и настройки берутся из upstream, дополнительные роли и fields — из его фактических списков. `False` сохраняет `!`; предварительный ограниченный запуск без репликации исключён. Криптографическая библиотека копируется byte-for-byte. Используется getToken/client, две фазы, S-pintok и A6/A1, E0/E1/E2 из research_proposal. Regex-подстановки шаблонов не используются.

## Диагностика достижимости

Шесть дополнительных inputs используют тот же генератор и те же процессы, но вместо основного correspondence вставляют один диагностический query:

```proverif
query u:UserHandle, r:RpID, a:AAGUID, c:bitstring, pkau:spkey;
  event(Server_Finish_Reg(u,r,a,c,pkau)).
```

либо для аутентификации:

```proverif
query u:UserHandle, r:RpID, a:AAGUID, c:bitstring;
  event(Server_Finish_Auth(u,r,a,c)).
```

Это документированная синтаксическая форма reachability в manual ProVerif §4.3.1. ProVerif выводит отрицание события. Поэтому `RESULT not event(...) is false` подтверждает достижимость события; ярлык ATTACK_OR_FALSE в машинной таблице **не является атакой** в этих шести случаях. Меняется только проверяемое утверждение, поведение процессов не меняется.

## Бюджет

Один baseline + один пилот + 12 основных + 6 диагностических = 20 модельных запусков ProVerif. Отдельные `-help` для версии и тесты собственного Python не входят в число модельных экспериментов. Если возникают timeout/UNKNOWN, исходный журнал сохраняется; повторения должны иметь новые IDs запусков и считаться отдельно.

## Подтверждённая дополнительная форма RESULT

В raw R05 ProVerif 2.05 выводит основное `RESULT inj-event(...) ==> inj-event(...) is false.` и затем `RESULT (even event(...) ==> event(...) is false.)`. Дополнительная строка проверена по официальному исходнику ProVerif 2.05, `src/display.ml`, функции `display_result_and_supplemental`, строки 2822–2850. Parser распознаёт этот supplementary формат и не подменяет им основной query. Первая консервативная версия parser помечала весь R05 UNKNOWN из-за незнакомой строки; raw metadata не переписывается. Processed summary всегда повторно разбирает полный raw и фиксирует SHA256 версии parser. Исправление parser не требует повторного запуска модели.

## Четыре дополнительные проверки точности

При timeout исходной конфигурации добавлены четыре отдельно маркированных запуска `precision.yaml`. Единственное дополнительное средство — **официальный** ProVerif CLI `-set preciseActions true`. Подтверждение синтаксиса: ProVerif 2.05 src/main.ml / Arg.parse / -set, строки 1345–1346; значения параметра: src/pitsyntax.ml:4474–4478; семантика: manual §6.2 и §6.7 / settings (локальный manual.txt:5638–5650). Настройка повышает точность аппроксимации, может увеличить время и не гарантирует разрешение UNKNOWN. PV/PVL-файлы остаются теми же; это отдельная ось чувствительности анализатора, а не новая threat assumption или upstream FIDO2Verif flag.

Выбраны A1 E0 и достижимость finish в регистрации E0/E2 и аутентификации E0. Timeout 30 s. С учётом всех исходных запусков общий бюджет составляет **24 модельных запуска**. Default результаты не переписываются и не заменяются precision-результатами.

## Продолжение: три положительных свидетеля достижимости

После нового указания пользователя «продолжай» исходный завершённый набор из 24 запусков не переписывается. Добавляется отдельная серия из трёх узких диагностик `witnesses.yaml`, чтобы проверить открытый вопрос невакуозности, а не расширять основную матрицу угроз. Максимум по завершении этой серии — 27 запусков, из них 24 первоначальных и 3 последующих; превышение первоначального целевого бюджета на три запуска обусловлено этой конкретной диагностической задачей.

В отдельной generated-копии меняется **единственное** точное вхождение `!system(` на `system(`. Перед изменением проверяется, что вхождение ровно одно. Это явное ограничение корневой репликации одной сессией, без regex и без изменения библиотеки, полей, ролей, параметров CTAP и аргументов событий. Проверяются только диагностические query D-finish для регистрации E0/E2 и аутентификации E0; режим запрещён для любых security queries. Команда использует подтверждённый `-set preciseActions true`.

Методическое основание: репликация допускает исполнение одной копии. Поэтому **положительный исполнимый trace**, достигающий события в модели с одной корневой сессией, можно вложить в исходную модель, оставив остальные копии неактивными. Это доказывает существование исполнения до события в исходной модели. Обратный перенос запрещён: true/недостижимость/секретность в ограниченной модели не доказывают свойства неограниченной модели. UNKNOWN и trace с дополнительной hypothesis не принимаются за свидетельство. Raw и основной результат сохраняются независимо от исхода.
